# Solution Overview — NEXORA AI

## 1. Three-Input Risk Engine

NEXORA AI's core is a 7-factor risk scoring engine that ingests three real-time data streams for every monitored asset and produces an explainable risk score from 0–100 with a named list of contributing factors.

**Sensor data** (weight: configurable, default ~35%): Each asset has IoT sensors measuring oil temperature, voltage, current load, vibration, and humidity. The engine flags sensor failures, outlier readings (outside calibrated normal ranges), and missing data — each contributing different amounts to the risk score. A sensor failure alone raises the score significantly because it signals either equipment distress or monitoring loss.

**Weather forecasts** (weight: ~30%): The system ingests weather records per district. Storm alerts add +20 points, flood alerts +25, extreme weather +30, heatwave +15, lightning risk +20. Multiple simultaneous alerts stack. This means a transformer that is marginal under normal conditions can become critical the moment a cyclone warning is issued for its district.

**Historical incidents** (weight: ~15%): Every past outage, transformer failure, and tripping event is stored per asset. Recurring incidents (same failure cause appearing multiple times) apply a higher multiplier than one-off events. Recent incidents (within 90 days) add more than older ones. This is what makes the system learn from the grid's own history.

**Supporting factors**: Asset age (older = higher base score), load ratio (current load vs rated capacity — above 85% triggers escalation), and worker field observations (the most nuanced input — trained workers submit structured observations including overheating, oil leakage, poor earthing, water ingress, each mapped to specific risk deltas).

Every prediction is stored with a full input snapshot, is versioned (`model_version` field), and requires administrator review before any maintenance action is taken. Admins can approve, reject, or override (with a mandatory written reason) — providing the human-in-the-loop governance required for high-stakes infrastructure decisions.

## 2. Grid-Impact Ranking & Maintenance Priority Queue

Risk score alone is not sufficient for prioritisation. A 65-point risk score on an asset serving 200 customers is less urgent than a 60-point score on an asset serving 15,000 customers including a hospital.

NEXORA AI computes a separate **Grid Impact Severity** score (0–100) based on connected customers, critical facilities served (hospitals, water pumping stations, rail yards), and the asset's position in the network topology. This is stored independently on the asset record and updated every time risk is recomputed.

The **Maintenance Priority Queue** ranks assets using a weighted formula:

```
Priority = risk_score × 0.4 + grid_impact × 0.3 + failure_probability × 100 × 0.2 + urgency_factor × 0.1
```

The queue is displayed as a sortable, filterable table with both scores shown side by side, so field managers can see at a glance whether a high-risk asset is in a dense urban area (high grid impact) or a rural setting (lower grid impact). State admins see only their state's queue; super admins see the national view across all 36 states.

Each queue entry includes: the recommended maintenance action (generated by the risk engine), the top 3 contributing factors, the required skill and tools, and the approval status. Approve, Reject, and Modify actions are available per plan with full audit trail.

## 3. Crew Pre-Positioning Workflow

The Crew Pre-Positioning screen addresses the U1 requirement for proactive crew deployment. It operates as follows:

1. **Weather triggers**: When active weather alerts exist for any district, the system generates a pre-positioning banner: *"Pre-position electrical crew in [District] — Storm forecast, 3 high-risk assets in area. Recommended staging: [district HQ]."*

2. **Plan selection**: The left panel shows all high/critical approved maintenance plans that need crew assignment. Clicking a plan loads the right panel.

3. **Worker matching**: The system queries qualified workers filtered by `field_of_work` matching the plan's required skill. Workers are tagged by proximity: **Local** (same district), **Same state**, or **Out of district** — giving dispatchers the information they need to minimise travel time.

4. **Assignment**: Clicking "Assign" calls `POST /api/maintenance/plans/:id/crew` to create a crew assignment record. All assignments are logged in the audit trail.

The crew planning page is accessible to both super admins (national view) and state admins (their state only), enforced by the same state isolation middleware that governs all API endpoints.
